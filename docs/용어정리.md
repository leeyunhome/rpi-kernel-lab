# 용어 정리

실습 중 나온 약어와 개념을 풀어서 정리한다. 다른 문서에서 용어가 나오면 여기를 참조.

---

## 인터럽트 기초

### 인터럽트(interrupt)란

CPU가 일하는 도중에 하드웨어가 "처리할 일이 생겼다"고 끼어드는 신호.

인터럽트가 없다면 CPU는 **폴링(polling)** — 즉 "데이터 왔나? 안 왔네. 왔나? 안 왔네"를 계속 반복해서 확인해야 한다. 이건 CPU를 낭비한다. 인터럽트 방식은 장치가 필요할 때만 CPU를 부르므로, 그 사이 CPU는 다른 일을 할 수 있다.

### IRQ

**I**nterrupt **R**e**Q**uest (인터럽트 요청). 인터럽트 신호에 붙은 번호.

장치마다 번호가 다르므로 커널은 번호만 보고 어느 장치에서 온 신호인지 판단한다.

### 인터럽트 핸들러(handler)

특정 IRQ가 발생했을 때 실행되는 함수. 드라이버가 `request_irq()` 계열 함수로 "이 번호가 오면 이 함수를 불러달라"고 커널에 등록한다.

### 인터럽트 컨텍스트

인터럽트 핸들러가 실행되는 동안의 특수한 실행 상태. 이 구간에서는 **잠들 수 없다**(sleep 불가). 다른 인터럽트를 막고 있는 상태이므로, 여기서 오래 머무르면 시스템 전체 응답성이 나빠진다. 그래서 핸들러는 최소한만 하고 빠져나오도록 설계한다.

## 하드웨어 관련 약어

| 약어 | 원말 | 설명 |
|---|---|---|
| **GIC** | **G**eneric **I**nterrupt **C**ontroller | ARM이 정한 표준 인터럽트 컨트롤러. 여러 장치가 동시에 인터럽트를 보낼 때 우선순위를 정하고 어느 CPU로 보낼지 결정하는 "교통정리" 하드웨어. `GICv2`는 버전 2. |
| **IPI** | **I**nter-**P**rocessor **I**nterrupt | CPU 코어끼리 주고받는 인터럽트. 멀티코어에서 "다른 코어야, 이 함수 좀 실행해줘"(function call), "스케줄링 다시 해"(rescheduling) 같은 요청에 쓴다. |
| **MSI** | **M**essage **S**ignaled **I**nterrupt | 전용 전선(핀)을 흔드는 대신 **메모리에 정해진 값을 써서** 인터럽트를 알리는 방식. 전선 개수 제약이 없어 PCIe 같은 최신 버스에서 쓴다. |
| **PCIe** | **P**eripheral **C**omponent **I**nterconnect **e**xpress | 고속 주변장치 연결 버스 규격. Pi 4에서는 USB 컨트롤러가 여기 붙어 있다. |
| **xHCI** | e**x**tensible **H**ost **C**ontroller **I**nterface | USB 3.0 이상을 지원하는 표준 USB 컨트롤러 규격. Pi 4가 이걸 쓰고, Pi 3는 구형 `dwc_otg`를 썼다. |
| **DMA** | **D**irect **M**emory **A**ccess | CPU를 거치지 않고 장치가 메모리에 직접 읽고 쓰는 방식. CPU 부하를 줄인다. |
| **SoC** | **S**ystem **o**n **C**hip | CPU·GPU·메모리 컨트롤러 등을 한 칩에 통합한 것. Pi 4는 BCM2711, Pi 3B는 BCM2837. |
| **PMU** | **P**erformance **M**onitoring **U**nit | CPU 안에 내장된 성능 측정 하드웨어. 사이클 수, 명령어 수, 캐시 미스 등을 센다. `perf`가 이걸 읽는다. |

## IRQ 번호 두 종류

같은 인터럽트에 번호가 **두 개** 붙는다. 이 구분이 실습에서 중요했다.

| 구분 | 설명 | 안정성 |
|---|---|---|
| **논리 IRQ 번호** | 커널이 부팅 중 드라이버 등록 **순서대로** 배정하는 번호. `/proc/interrupts` 맨 왼쪽 숫자. | ❌ 커널 버전·드라이버 구성이 바뀌면 달라짐 |
| **hwirq** (하드웨어 IRQ) | 인터럽트 컨트롤러 입장에서의 실제 물리 번호. 회로 설계에 고정됨. | ✅ 하드웨어가 같으면 동일 |

**예시**: 이 보드에서 `fe00b880.mailbox`는 논리 IRQ 14 / hwirq 65. 참고 자료의 저자 장비(같은 Pi 4, 커널 4.19)에서는 논리 IRQ 31 / hwirq 65였다. **하드웨어 번호는 같고 논리 번호만 다르다.**

그래서 코드에 `if (irq == 31)`처럼 논리 번호를 하드코딩하면 커널만 바뀌어도 깨진다. 드라이버는 `platform_get_irq()` 같은 API로 번호를 **런타임에 조회**해야 한다.

## 트리거 방식: Level vs Edge

장치가 전기 신호로 "인터럽트 발생"을 알리는 두 가지 방식.

| 방식 | 동작 | 비유 |
|---|---|---|
| **Level (레벨 트리거)** | 신호가 **켜져 있는 동안** 계속 인터럽트로 인식. 핸들러가 처리하고 장치가 신호를 내려야 끝남. | 손을 계속 들고 있기 |
| **Edge (에지 트리거)** | 신호가 **바뀌는 순간**(꺼짐→켜짐)만 인식. 한 번 알리고 끝. | 종을 한 번 치기 |

Level은 놓칠 염려가 적지만 장치가 신호를 안 내리면 무한 반복될 수 있고, Edge는 처리가 빠르지만 신호가 겹치면 놓칠 수 있다.

## 커널이 만드는 가짜 파일시스템

디스크에 실제로 있는 파일이 아니라, **커널이 자기 내부 상태를 파일처럼 보여주는** 인터페이스다. `cat`으로 읽는 순간 커널이 값을 만들어서 준다.

| 경로 | 정식 명칭 | 용도 |
|---|---|---|
| `/proc` | procfs (**proc**ess **f**ile**s**ystem) | 프로세스 정보와 커널 상태. `/proc/interrupts`, `/proc/cpuinfo` 등 |
| `/sys` | sysfs (**sys**tem **f**ile**s**ystem) | 장치·드라이버를 계층 구조로 노출. `/sys/kernel/irq/14/` 처럼 항목마다 폴더 |
| `/sys/kernel/debug` | debugfs (**debug** **f**ile**s**ystem) | 디버깅 전용. ftrace가 여기 있음 |

## ftrace 관련

### ftrace

**f**unction **trace**r. 커널에 내장된 추적 도구. 별도 프로그램 설치 없이 `/sys/kernel/debug/tracing/` 아래 파일을 읽고 쓰는 것만으로 커널 동작을 들여다볼 수 있다.

### tracer 종류

| tracer | 하는 일 |
|---|---|
| `nop` | 아무것도 안 함 (기본값, 꺼진 상태) |
| `function` | 커널 함수가 호출될 때마다 기록 |
| `function_graph` | 함수의 **진입과 종료**를 들여쓰기로 기록 — 호출 트리 형태로 보임 |

### tracepoint

커널 소스 곳곳에 미리 심어둔 **관측 지점**. 예: `irq_handler_entry`(인터럽트 핸들러 진입), `sched_switch`(컨텍스트 스위치). 평소엔 꺼져 있어 오버헤드가 거의 없고, 켜면 그 지점을 지날 때마다 기록된다.

`function_graph`가 "모든 함수를 다 본다"면, tracepoint는 "중요한 지점만 골라 본다"에 가깝다.

## 커널 빌드 관련

| 용어 | 설명 |
|---|---|
| **`.config`** | 커널 빌드 설정 파일. 어떤 기능을 켜고 끌지, 무엇을 커널에 내장하고 무엇을 모듈로 뺄지 정의 |
| **defconfig** | **def**ault **config**. 보드별 기본 설정 템플릿. `bcm2711_defconfig`는 Pi 4용 |
| **olddefconfig** | 기존 `.config`를 유지하되, 새 커널 버전에서 추가된 항목만 기본값으로 채움 |
| **mrproper** | 소스 트리를 완전히 초기화 (`.config` 포함 모든 빌드 산출물 삭제). `clean`보다 강력 |
| **out-of-tree 빌드** | `make O=<디렉터리>`로 산출물을 소스와 **다른 폴더**에 만드는 방식. 소스 트리가 깨끗하게 유지됨 |
| **모듈 (`.ko`)** | **k**ernel **o**bject. 커널에 내장하지 않고 필요할 때 `insmod`로 올렸다 내렸다 하는 부품 |
| **DTB** | **D**evice **T**ree **B**lob. 보드에 어떤 하드웨어가 어떻게 붙어 있는지 기술한 데이터를 컴파일한 것. ARM은 x86과 달리 하드웨어를 자동 탐지하기 어려워서 이런 "설명서"가 필요하다 |
| **dtsi / dts** | Device Tree **S**ource (**I**nclude). DTB의 원본 텍스트 파일 |
| **overlay (`.dtbo`)** | 기본 DTB 위에 덧씌우는 조각. 카메라·디스플레이 같은 선택적 장치를 켤 때 사용 |
| **initramfs** | **init**ial **RAM** **f**ile **s**ystem. 진짜 루트 파일시스템을 마운트하기 전에 임시로 쓰는 메모리상의 파일시스템 |

## 스케줄링 관련

| 용어 | 설명 |
|---|---|
| **컨텍스트 스위치** | CPU가 실행 중인 작업을 바꾸는 것. 현재 상태를 저장하고 다음 작업 상태를 복원 |
| **preempt (선점)** | 실행 중인 작업을 강제로 중단시키고 다른 작업으로 넘어가는 것 |
| **preempt_count** | 선점 비활성화 중첩 횟수. 0보다 크면 "지금 끼어들면 안 되는 구간" |
| **softirq** | 인터럽트 핸들러가 급한 일만 하고 넘긴 **나머지 작업**. 인터럽트 컨텍스트에서 벗어나 조금 여유롭게 처리 |
| **threaded IRQ** | 인터럽트 처리를 아예 별도 **커널 스레드**로 돌리는 방식. `irq/14-mailbox` 같은 이름으로 프로세스 목록에 보인다 |
| **top half / bottom half** | 인터럽트 처리를 둘로 나누는 설계. 상반부(top)는 급한 것만 즉시, 하반부(bottom)는 나머지를 나중에 |
| **어피니티(affinity)** | 특정 인터럽트나 프로세스를 어느 CPU 코어에서 처리할지 지정하는 설정 |
| **RT 우선순위** | **R**eal**T**ime 우선순위. 일반 작업보다 먼저 실행되도록 보장 |
