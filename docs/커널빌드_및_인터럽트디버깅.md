# 커널 빌드 — 소스 확보부터 빌드 완료까지

> 모르는 용어가 나오면 [`용어정리.md`](용어정리.md) 참고.

> 시행착오 순서대로 기록한다. 빌드는 완료했고, 설치·인터럽트 디버깅은 이어서 추가 예정.

## 목표

Raspberry Pi 4B에서 실행 중인 커널(`6.12.25+rpt-rpi-v8`)과 최대한 동일한 소스로 **직접 빌드/설치**한다. 이렇게 하면:

1. 커널 소스에 코드를 넣어 동작을 관찰할 수 있다 (예: 인터럽트 핸들러 등록 시점에 `printk`/`dump_stack()` 삽입)
2. 디버그 심볼이 붙은 커널을 확보해 `crash` 유틸리티로 커널 자료구조(`task_struct`, `irq_desc` 등)를 들여다볼 수 있다 — 배포판 기본 커널에는 `/usr/lib/debug/boot/`가 없어 이게 막힌다
3. 커널 설정(`.config`)을 바꿔가며 기능 유무에 따른 차이를 직접 확인할 수 있다

최종적으로는 threaded IRQ·softirq 등 인터럽트 서브시스템을 코드 레벨에서 추적하는 것이 목표다.

## 환경

- Raspberry Pi 4B Rev 1.2, 4코어, RAM 1.8Gi(2GB), swap 511Mi
- 커널: `6.12.25+rpt-rpi-v8` (aarch64, Raspberry Pi Foundation 표준 빌드)
- 저장공간: 102GB 여유 (`/dev/mmcblk0p2`, 117G 파티션)
- OS: Debian(Raspbian) Bookworm, `/boot/firmware/` 레이아웃(구형 `/boot/` 직접 방식이 아님)

## 시행착오

### 1. `rpi-source` 도구 — Python 2 유산이라 즉시 실패

Raspberry Pi Foundation이 "실행 중인 커널과 정확히 일치하는 소스"를 자동으로 받아오는 공식 도구가 있어서 시도했으나:

```
File "/usr/local/bin/rpi-source", line 111
    except urllib2.HTTPError, e:
SyntaxError: multiple exception types must be parenthesized
```

Python 2 문법(`except X, e:`)으로 작성된 오래된 스크립트라 이 시스템의 Python 3에서 바로 죽는다. 오랫동안 유지보수가 끊긴 도구로 판단, **수동 git clone으로 전환**.

### 2. 수동 clone은 성공, 브랜치 `rpi-6.12.y`

```
git clone --depth=1 -b rpi-6.12.y https://github.com/raspberrypi/linux .
```

258MB 다운로드, 87,451개 파일 체크아웃. 완료 후 `git log`로 커밋 시각 확인.

### 3. `make bcm2711_defconfig` 실패 — `flex` 누락

```
LEX     scripts/kconfig/lexer.lex.c
/bin/sh: 1: flex: not found
make[1]: *** [Makefile:696: bcm2711_defconfig] Error 2
```

`bison`과 함께 설치 후 재시도하여 해결.

### 4. `oldconfig` vs `defconfig` — 두 가지 유효한 경로

처음엔 "실행 중인 커널의 `/proc/config.gz`를 재사용 + `make oldconfig`"로 진행하려 했으나, 이 커널은 `CONFIG_IKCONFIG_PROC`가 꺼져 있어 `/proc/config.gz` 자체가 없었다 (`/boot/config-<버전>`은 존재).

한편 이미 `make bcm2711_defconfig`가 성공해서 `.config`가 만들어진 상태였는데, **이건 `oldconfig`가 필요 없는 별개의 경로**다 — `defconfig`는 기존 설정과 무관하게 템플릿에서 새로 생성하고, `oldconfig`는 기존 설정을 새 소스 버전에 맞게 증분 갱신하는 것이라 애초에 같이 쓸 이유가 없다. 두 방법을 섞어서 혼선이 있었으나, **네이티브 빌드(크로스컴파일 아님)에서는 `make`가 호스트 아키텍처(`aarch64`)를 자동 인식**하므로 `bcm2711_defconfig`도 arm64용으로 정상 생성됨을 확인.

### 5. 문서의 `KERNEL=kernel7l`은 이 장비에 안 맞음 (32비트용)

공식 문서의 안내 순서를 따라가다 `KERNEL=kernel7l`을 설정했는데, 이 값은 **32비트 ARMv7** 커널 이미지 이름이다. 이 장비는 `aarch64`(64비트)로 부팅 중이라 올바른 값은 `kernel8`이다. 다행히 이 시점엔 이 변수가 아직 어디에도 쓰이지 않아 실질적 영향은 없었음 — 설치 단계에서 파일명을 명시적으로 지정할 때만 문제가 될 상황이었다.

### 6. 디렉터리 구조를 책과 맞추기 위한 재구성

`git clone ... .`(현재 디렉터리에 바로 clone)으로 진행해 `rpi_kernel_src/` 바로 아래 소스가 풀렸는데, 참고 중인 책은 `cd linux`로 하위 폴더 진입을 전제로 한다. `rpi_kernel_src/linux/`로 전체를 재배치해 구조를 맞춤 (같은 파일시스템 내 이동이라 빠르게 완료).

### 7. 빌드 의존성이 단계별로 하나씩 드러남

빌드를 시작한 뒤에도 필요한 패키지가 한 번에 다 드러나지 않고, **컴파일이 그 지점에 도달해서야** 하나씩 실패했다.

| 실패 지점 | 에러 | 필요 패키지 |
|---|---|---|
| `scripts/kconfig` 빌드 | `flex: not found` | `flex`, `bison` |
| `objtool` 관련 | `fatal error: libelf.h: No such file` | `libelf-dev` |
| `certs/extract-cert` | `fatal error: openssl/bio.h: No such file` | `libssl-dev` |

특히 마지막 `openssl/bio.h`는 **빌드가 상당히 진행된 뒤에야** 나왔다(모듈 서명용 인증서 생성 단계). `-j6` 병렬 빌드라 로그가 뒤섞여서, 최상위 `Error 2`가 찍힌 위치와 실제 원인 메시지가 수십 줄 떨어져 있었다 — **병렬 빌드에서 에러를 찾을 때는 `Error 2`가 아니라 `fatal error`/`error:` 패턴을 거슬러 올라가 찾아야 한다.**

### 8. out-of-tree 빌드는 소스 트리가 깨끗해야 시작된다

`make O=<dir>` 방식으로 전환했더니 이렇게 거부당했다:

```
*** The source tree is not clean, please run 'make mrproper'
```

앞서 in-tree로 `make bcm2711_defconfig`를 돌린 흔적이 소스 트리에 남아 있었기 때문이다. `make mrproper`로 소스 트리를 정리한 뒤에야 진행됐다. (이때 `.config`는 이미 출력 폴더로 복사해둔 상태라 안전했다.)

### 9. RAM 2GB에서 `-j6`은 스와핑을 유발했다

빌드 중반에 부하를 재보니:

```
load average: 33.65, 30.53, 19.82     # 4코어 장비에서 정상치의 8배
MiB Swap: 512.0 total, 6.8 free, 505.2 used   # 스왑 99% 사용
```

이 구간에서는 **새 SSH 접속이 120초 안에 수립되지 못할 정도**로 시스템이 느려졌다(기존 세션은 유지됨). 스와핑이 걸리면 CPU 병목이 아니라 디스크 I/O 병목이 되어, `-j6`가 오히려 역효과를 낸다. 다행히 OOM 없이 통과했지만, **RAM 2GB 보드에서는 `-j2`~`-j4`가 더 안전한 선택**이었을 것이다.

이후 컴파일 대상이 작은 파일들로 넘어가며 부하는 자연스럽게 회복됐다(load 33 → 6).

## 설치 준비 — 책과 다른 점

참고 자료의 설치 스크립트는 32비트 Pi 3B 기준이라 경로·파일명이 전부 다르다. 또한 원본 커널을 **그대로 덮어쓰는** 방식이라 부팅 실패 시 되돌릴 방법이 없다.

| 항목 | 참고 자료 (32비트) | 이 장비 (arm64) |
|---|---|---|
| 아키텍처 경로 | `arch/arm/` | `arch/arm64/` |
| 커널 이미지 | `zImage` → `kernel7.img` | `Image.gz` → `kernel8.img` |
| DTB 경로 | `arch/arm/boot/dts/*.dtb` | `arch/arm64/boot/dts/broadcom/*.dtb` |
| 부팅 파티션 | `/boot/` | `/boot/firmware/` |

[`scripts/install_kernel.sh`](../scripts/install_kernel.sh)는 위 경로 차이를 반영하고, 여기에 **롤백 경로**를 추가했다:

1. 원본 `kernel8.img`·`config.txt`를 `.orig`로 백업 (`cp -n`이라 재실행해도 덮어쓰지 않음)
2. 새 커널을 원본이 아닌 **`kernel8-custom.img`** 로 설치
3. `config.txt`에 `kernel=kernel8-custom.img` 추가해 이걸 쓰도록 지정

부팅에 실패해도 SD카드를 PC에 꽂아 `config.txt`에서 그 한 줄만 지우면 원래 커널로 돌아온다 — 부팅 파티션이 FAT이라 Windows에서도 편집 가능하다.
