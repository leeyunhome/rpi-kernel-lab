# 인터럽트 디스크립터 조회 — 커널 패치 없이 sysfs로

> 모르는 용어가 나오면 [`용어정리.md`](용어정리.md) 참고.

> 참고 자료는 커널 소스에 `printk`를 심고 재빌드·재설치해서 `irq_desc`를 확인한다. 이 문서는 **커널 교체 없이** 같은 정보를 얻는 경로를 정리하고, 그 과정에서 드러난 IRQ 번호 문제를 기록한다.

## 배경: 이 실습을 sysfs로 한 이유

참고 자료의 실습은 `drivers/mailbox/bcm2835-mailbox.c`에 아래 같은 함수를 추가하고 커널을 다시 빌드·설치하는 방식이다.

```c
desc = irq_to_desc(irq_num);
action = desc->action;
printk("irq num: %d name: %8s\n", action->irq, action->name);
printk("interrupt handler: %pF\n", action->handler);
```

즉 `irq_desc` → `action` 필드에 들어있는 **핸들러 이름과 인자**를 커널 로그로 찍어보는 것이 목적이다.

이 보드는 **물리적 접근이 불가능한 상태**(전원 재투입·SD카드 탈착 불가)라 커널 교체 후 부팅 실패 시 복구 경로가 없다. 그래서 커널을 건드리지 않고 같은 정보에 도달하는 방법을 택했다.

## 결론: 대부분 `/sys/kernel/irq/`에 이미 노출돼 있다

```
$ for f in /sys/kernel/irq/14/*; do printf "%-16s : %s\n" "$(basename $f)" "$(cat $f)"; done
actions          : fe00b880.mailbox
chip_name        : GICv2
hwirq            : 65
name             :
per_cpu_count    : 86787,0,0,0
type             : level
wakeup           : disabled
```

| 참고 자료가 `printk`로 출력하려던 것 | sysfs 경로 |
|---|---|
| `action->name` | `actions` |
| `desc->irq_data` (하드웨어 번호) | `hwirq` |
| 인터럽트 컨트롤러 종류 | `chip_name` |
| 트리거 방식 | `type` |
| (책엔 없음) CPU별 발생 횟수 | `per_cpu_count` |
| **`action->handler`** (함수 포인터) | **없음** — 커널 내부 주소라 미노출 |

핸들러 함수 주소만 sysfs로 볼 수 없다. 그건 커널 패치나 `crash` 유틸리티가 필요하다. **나머지는 재빌드 없이 전부 확인 가능하다.**

커널 4.19 시절 자료가 커널 패치를 요구했던 부분이, 6.12에서는 sysfs 인터페이스로 상당 부분 대체됐다는 뜻이다.

## 발견 1 — IRQ 번호는 같은 보드에서도 달라진다

참고 자료의 저자는 "책의 `irq == 56 || irq == 86`을 Pi 4에서는 `irq == 31 || irq == 35`로 바꿔야 한다"고 안내한다. 그런데 **그 번호도 이 장비에서는 맞지 않는다.**

| 장치 | 책 (Pi 3B, 4.19) | 저자의 Pi 4 (4.19) | **이 장비 (Pi 4, 6.12)** |
|---|---|---|---|
| `fe00b880.mailbox` | — | IRQ **31** | **IRQ 14** |
| `brcmstb_thermal` | — | IRQ **35** | **존재하지 않음** |
| `uart-pl011` | — | IRQ 34 | IRQ 39 |
| `eth0` | — | IRQ 44, 45 | IRQ 28, 29 |
| `mmc1, mmc0` | — | IRQ 36 | IRQ 40 |
| `dwc_otg` | IRQ 56 | 없음 (xHCI로 대체) | 없음 |

**같은 Pi 4 보드인데도 논리 IRQ 번호가 전부 다르다.** 반면 하드웨어 번호는 일치한다 — mailbox는 양쪽 다 GICv2 65번이다.

이유는 **논리 IRQ 번호가 부팅 시 드라이버 등록 순서에 따라 동적으로 배정**되기 때문이다. 커널 버전이 다르면 드라이버 초기화 순서와 활성화된 드라이버 목록 자체가 달라지므로 번호도 밀린다.

> **교훈**: IRQ 번호를 코드에 하드코딩하면 같은 보드에서도 커널 버전이 바뀌는 순간 깨진다. 책 → 저자의 Pi 4 → 이 장비, 세 단계에 걸쳐 번호가 계속 바뀐 것이 실물로 확인됐다. 드라이버에서 IRQ를 얻을 때 `platform_get_irq()` 같은 API를 쓰는 이유가 이것이다.

## 발견 2 — `/proc/interrupts`에 안 보이는 것들이 sysfs에는 있다

sysfs로 전체를 훑으니 `/proc/interrupts`에는 없던 항목이 두 종류 나왔다.

**① IPI가 실제 IRQ 번호를 갖고 있다**

`/proc/interrupts`는 IPI를 `IPI0`~`IPI7`이라는 별도 블록으로 표시하지만, sysfs에서는 **IRQ 1~8**로 등록돼 있다.

```
1     GICv2  0   edge  IPI   33289,34433,36874,34303
2     GICv2  1   edge  IPI   752509,5997627,9505772,6923089
...
```

즉 코어 간 인터럽트도 내부적으로는 일반 인터럽트와 동일한 `irq_desc` 자료구조로 관리된다.

**② 핸들러가 없는 빈 디스크립터**

```
23    GICv2  128  edge   (null)   0,0,0,0
24    GICv2  145  level  (null)   0,0,0,0
25    GICv2  146  level  (null)   0,0,0,0
26    GICv2  180  level  (null)   0,0,0,0
```

`irq_desc`는 할당됐지만 `action`이 비어 있는 상태다. 커널이 인터럽트 디스크립터를 미리 만들어두고 드라이버가 나중에 `request_irq()`로 채우는 구조라 이런 빈 슬롯이 생긴다. `/proc/interrupts`는 핸들러가 등록된 것만 보여주므로 이들이 나타나지 않는다.

## 발견 3 — 인터럽트 컨트롤러가 3종류, 계층 구조를 이룬다

| 컨트롤러 | 담당 |
|---|---|
| `GICv2` | ARM 표준 컨트롤러 — 대부분의 주변장치 |
| `interrupt-controller@7ef00100` | HDMI 전용 서브 컨트롤러 (IRQ 42~49) |
| `BRCM STB PCIe MSI` | PCIe 장치용 MSI (xhci_hcd) |

HDMI 관련 인터럽트들이 GIC 밑에 달린 **별도 서브 컨트롤러**를 통해 전달된다. 계층형(chained) 인터럽트 컨트롤러의 실제 사례다.

## 발견 4 — 인터럽트가 CPU0에 몰려 있다

```
28  eth0              26514481,0,0,0
40  mmc1,mmc0          1178309,0,0,0
14  fe00b880.mailbox     86827,0,0,0
```

주변장치 인터럽트가 **전부 CPU0에서만** 처리되고 있다. 반면 코어별로 독립적인 것들은 고르게 분산된다:

```
11  arch_timer   35161918,3927526,4689299,4134803
2   IPI            752509,5997627,9505772,6923089
```

`arch_timer`는 코어마다 자기 타이머가 있고, IPI는 애초에 코어 간 통신이라 당연히 분산된다. 주변장치 인터럽트만 CPU0으로 고정된 것은 **인터럽트 어피니티(affinity) 설정** 때문이다.

`IPI1`(Function call interrupts)이 CPU2에서 950만 회로 유독 높은데, 직전에 `-j6` 커널 빌드로 4코어를 풀가동한 흔적으로 보인다.

## 정리

- 참고 자료가 커널 재빌드를 요구했던 `irq_desc` 조회는 **핸들러 함수 주소를 제외하면 sysfs로 대체 가능**하다.
- IRQ 논리 번호는 **커널 버전에 따라 같은 보드에서도 바뀐다.** 하드웨어 번호만 안정적이다.
- sysfs는 `/proc/interrupts`보다 많은 정보를 준다 — IPI의 실제 IRQ 번호, 핸들러 미등록 디스크립터, 컨트롤러 종류, 트리거 방식.
